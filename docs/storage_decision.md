# 영구 저장소 결정

## 선정 결과

Public Brief의 정제 데이터와 분석 결과는 **SQLite**에 저장한다.

- 저장 방식: SQLite
- 예정 파일: `data/public_brief.db`
- Python 연결 방식: 표준 라이브러리 `sqlite3`
- 별도 데이터베이스 서버: 필요 없음

## 영구 저장소란?

영구 저장소는 프로그램을 종료해도 데이터가 사라지지 않는 저장 공간이다.

Python의 List나 Dict에만 자료를 담으면 프로그램을 종료하는 순간 자료가 사라진다. SQLite를 사용하면 수집한 자료가 하나의 데이터베이스 파일에 저장되므로 다음 실행에서도 다시 사용할 수 있다.

## SQLite를 선택한 이유

- Python에 기본 포함된 `sqlite3`로 사용할 수 있다.
- 별도 서버나 계정 설정이 필요 없다.
- 하나의 파일로 저장되어 실행과 백업이 쉽다.
- URL을 기준으로 중복 자료를 빠르게 확인할 수 있다.
- 날짜, 분야, 중요도 조건으로 자료를 검색하기 쉽다.
- 기존 자료에 AI 요약과 분류 결과를 나중에 추가하거나 수정하기 쉽다.
- 일부 AI 처리가 실패한 자료만 찾아 다시 처리하기 쉽다.
- 프로젝트 규모의 데이터를 관리하기에 충분하다.

## JSONL과 비교

| 구분 | SQLite | JSONL |
|---|---|---|
| 저장 형태 | 하나의 데이터베이스 파일 | 한 줄에 JSON 객체 하나를 저장하는 텍스트 파일 |
| 검색 | SQL로 조건 검색 가능 | 파일을 처음부터 읽으며 직접 조건 확인 |
| 중복 확인 | URL에 UNIQUE 조건 적용 가능 | 기존 줄을 직접 순회하여 비교해야 함 |
| 자료 수정 | 원하는 행만 수정 가능 | 보통 전체 파일을 다시 작성해야 함 |
| 구조 관리 | 테이블과 컬럼으로 명확하게 관리 | 자유롭지만 항목 구조가 달라질 수 있음 |
| 사람이 직접 읽기 | 전용 도구나 SQL이 필요 | 텍스트 편집기로 쉽게 확인 가능 |
| 이 프로젝트 적합성 | 높음 | Raw 보관이나 단순 로그에는 적합 |

## 데이터 저장 구분

원본 데이터와 정제·분석 데이터는 다음과 같이 분리한다.

```text
data/
├── raw/                 # RSS에서 받은 원본 데이터
├── output/              # Markdown, CSV, Excel 결과물
└── public_brief.db      # 정제 데이터와 AI 분석 결과
```

- `data/raw/`: 수집 당시 원본을 변경하지 않고 보관한다.
- `data/public_brief.db`: 정제, 중복 제거, 요약, 분야 및 중요도 결과를 저장한다.
- `data/output/`: 사람이 읽거나 공유할 최종 결과물을 저장한다.

## 초기 테이블 설계 방향

구체적인 테이블은 저장소 모듈 구현 단계에서 확정한다. 기본적으로 다음 정보를 한 자료 단위로 관리한다.

- 내부 ID
- 제목
- 기관명
- 작성일
- 원문 URL
- 본문
- 수집 시각
- AI 핵심 요약
- 업무 영향
- 확인 필요 사항
- 분야
- 중요도
- 처리 상태
- 생성 및 수정 시각

오류는 자료와 분리된 오류 테이블에 저장하여 어떤 단계에서 어떤 자료가 실패했는지 추적할 수 있게 한다.

## 운영 원칙

- URL을 중복 확인 기준으로 사용하고 `UNIQUE NOT NULL` 조건을 적용한다.
- 데이터베이스 작업은 성공 시에만 확정한다.
- 저장 실패 시 오류 로그를 남긴다.
- 데이터베이스 파일은 코드와 분리하여 관리한다.
- 실제 수집 데이터베이스의 GitHub 포함 여부는 공개 범위와 용량을 확인한 뒤 결정한다.
