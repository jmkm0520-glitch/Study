# API와 RSS의 차이

## 한눈에 보기

| 구분 | API | RSS |
|---|---|---|
| 의미 | 프로그램이 조건을 보내 데이터를 요청하는 통로 | 사이트의 최신 글을 구독하는 표준 피드 |
| 비유 | 원하는 메뉴를 골라 주문하기 | 새로 나온 소식 목록을 받아보기 |
| 데이터 형식 | 주로 JSON 또는 XML | 주로 RSS 형식의 XML |
| 검색 조건 | 날짜, 검색어, 페이지 등 다양한 조건을 지원할 수 있음 | 제공자가 만든 최신 글 목록을 순서대로 받는 경우가 많음 |
| 인증 | API 키가 필요한 경우가 많음 | 인증 없이 공개되는 경우가 많음 |
| 호출 제한 | 일일 또는 분당 요청 횟수 제한이 있을 수 있음 | 별도 제한이 없더라도 적은 횟수로 요청해야 함 |
| 구현 난이도 | 인증, 페이지 이동, 오류 코드 처리가 필요할 수 있음 | 피드 주소와 항목 구조가 단순해 비교적 쉬움 |
| 제공 정보 | 서비스에 따라 상세하고 구조적인 데이터를 제공 | 제목, 링크, 작성일, 요약·본문 등 기본 정보 중심 |

## API란?

API는 프로그램끼리 정보를 주고받기 위한 공식 창구다. 프로그램이 날짜, 검색어, 페이지 번호 같은 조건을 요청에 담아 보내면 서버가 조건에 맞는 데이터를 돌려준다.

예를 들어 다음과 같이 요청할 수 있다.

```text
2026년 8월 1일부터 8월 31일까지의 보도자료 20개를 주세요.
```

실제 사용 시에는 API 키, 요청 주소, 검색 조건, 호출 횟수 제한을 확인해야 한다.

## RSS란?

RSS는 웹사이트가 최신 게시물을 일정한 XML 형식으로 제공하는 구독 목록이다. 프로그램은 RSS 주소에 접속하여 새 글의 제목, 날짜, 본문, 원문 링크 등을 읽는다.

RSS는 보통 복잡한 검색 조건을 보내기보다 피드에 포함된 최신 목록을 받아온 뒤, 필요한 날짜나 분야를 프로그램 내부에서 골라낸다.

## 공통점

- 사람이 웹사이트를 직접 방문하지 않아도 데이터를 받을 수 있다.
- 사이트가 공식적으로 제공하면 일반 웹 크롤링보다 구조가 안정적이다.
- 네트워크 오류에 대비한 timeout과 오류 처리가 필요하다.
- 제공자의 이용 정책과 요청 횟수 기준을 지켜야 한다.
- 받은 데이터의 출처와 원문 URL을 보존해야 한다.

## 이 프로젝트에서 RSS를 선택한 이유

Public Brief의 첫 데이터 소스는 보건복지부 보도자료 RSS 2.0이다.

- 별도의 API 키가 필요하지 않다.
- XML 구조가 단순해 첫 수집기를 만들기 쉽다.
- 제목, 작성일, 본문, 기관명, 원문 URL을 확보할 수 있다.
- AI 요약에 사용할 본문이 RSS에 포함되어 있다.
- 최신 보도자료를 정기적으로 확인하려는 프로젝트 목적에 적합하다.

## RSS의 한계와 처리 방법

### 날짜 검색 조건이 부족함

RSS 전체를 받은 뒤 프로그램에서 `--date-from`, `--date-to` 조건을 적용한다.

### 제공되는 글의 수가 제한될 수 있음

RSS가 제공하는 범위 안에서 수집한다. 더 오래된 자료가 필요하면 이후 공식 API 추가를 검토한다.

### 카테고리가 없을 수 있음

이 프로젝트에서는 수집 후 AI 분류 단계에서 사전 정의된 카테고리를 생성한다.

### 피드 구조가 바뀔 수 있음

필수 필드 검증과 오류 로그를 구현하여 구조 변경을 발견할 수 있게 한다.

## 결론

첫 구현에서는 접근과 구조가 단순한 RSS가 적합하다. 향후 세밀한 검색, 대량 데이터 또는 과거 데이터가 필요해지면 공식 API를 추가하는 방식으로 확장한다.
